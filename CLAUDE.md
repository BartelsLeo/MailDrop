# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MailDrop is a **Visual Studio Tools for Office (VSTO) Outlook Add-in** written in Visual Basic .NET that files emails and attachments into project folder structures. It uses a BERT model (via ONNX) to suggest mail drop configuration.

- **Language**: Visual Basic .NET, .NET Framework 4.7.2, VSTO 4.0
- **Host**: Microsoft Outlook
- **Build tool**: MSBuild / Visual Studio 2022

## Features

- Outlook ribbon button MailDrop opens a right-side task pane.
- The add-in reacts to selection changes and enables editing only when exactly one mail is selected.
- Session data is prepared from the selected mail metadata (Betreff, Absender, AbsenderDomain, Empfaenger, Datum).
- ProjektPfad offers recent project folders for the current user (from SQLite history) plus anderes... via folder picker.
- ProjektstrukturPfad is selected from a TreeView that is built dynamically from the selected ProjektPfad. The TreeView area is 300px tall (was 150px), to show more of the structure without scrolling.
- The TreeView's root level is not the direct children of ProjektPfad but a single synthetic root node (`DirectoryTreeHelper.BuildDirectoryTree`, `RelativePath=String.Empty`, `FullPath=ProjektPfad`, always expanded regardless of `expandByDefault`) whose Children are the former first level. Its displayed `Name` is the real folder name of the selected ProjektPfad (`GetProjektPfadDisplayName`: `Path.GetFileName` after trimming a trailing separator, so a path a folder picker might return with one, e.g. `C:\Projekte\P-1\`, doesn't collapse to an empty name; falls back to the trimmed full path only in the degenerate case of a bare drive root like `C:\`) - not a fixed "Projektpfad" label, so the node reads like any other folder in the tree instead of a special placeholder. Reason for the node's existence at all: WPF's TreeView has no built-in way to clear its selection (e.g. by clicking empty space), so once any subfolder was selected there was no way back to targeting ProjektPfad itself for "Neuer Ordner" or as the ProjektstrukturPfad. Selecting this root node sets `Session.ProjektstrukturPfad = String.Empty`, which `InputChecker.CheckInput` treats as a valid selection distinct from `Nothing` ("nothing selected yet") - OK then files directly into ProjektPfad. The root node itself cannot be deleted or renamed (`DeleteSelectedFolder`/`RenameSelectedFolder` reject a selected node whose `RelativePath` is empty with a message box); "Neuer Ordner" on it (or with nothing selected) still creates a folder directly under ProjektPfad, unchanged. (All of this keys off `RelativePath`, not `Name` - the display-name change doesn't touch any selection/guard logic.)
- ProjektstrukturPfad TreeView supports creating, deleting, and renaming folders via context menu actions (Neuer Ordner, Loeschen, Umbenennen), and also supports creating folders via a Neuen Ordner button; if a node is selected, operations target that node (the synthetic root node included, for Neuer Ordner), otherwise creation defaults to ProjektPfad.
- Creating, deleting, and renaming a folder (Neuer Ordner/Neuen Ordner, Loeschen, Umbenennen) no longer trigger a full BuildDirectoryTree() rebuild of the whole TreeViewData tree. Instead, all three actions call the same MailDropWpfTaskPane.RefreshTreeChildren(parentPath) helper right after the filesystem change, which calls Session.RefreshTreeViewChildren -> DirectoryTreeHelper.RefreshChildren: this re-reads only the direct children of the affected parent folder from disk (Directory.GetDirectories) and replaces just that node's Children collection (or the synthetic root node's Children, if the parent is ProjektPfad itself) - reusing CreateDirectoryNodeWithExpand per rediscovered child so nested subtrees are populated normally. Everything outside that one parent's children (siblings, ancestors, other branches) is left untouched and keeps its expanded/collapsed TreeViewItem state. This one mechanism intentionally covers all three actions uniformly - the caller only needs to know which folder's contents changed (the parent of the created/deleted/renamed node), not how the tree needs to change, which is more robust than action-specific node surgery (in particular for rename, where a manual approach would otherwise have to update Name/FullPath/RelativePath on the renamed node and recursively on every descendant). The trade-off: nodes strictly below the affected parent are fully rebuilt and lose their own expand/collapse state (IsExpanded is reset to the level<=2-relative-to-that-parent default via CreateDirectoryNodeWithExpand) - this is scoped to the folder actually being edited, not the rest of the tree. If the affected parent is ProjektPfad itself, this means the entire root level (and everything below it) is rebuilt, since "the parent's children" is the whole first level in that case. RefreshTreeViewChildren/RefreshChildren return False if the parent folder can't be located in the current tree (should not normally happen); the UI helper falls back to the old full BuildDirectoryTree() rebuild in that case.
- Titel and Absender (kurz) are editable text fields used by placeholder resolution.
- Ablageordner and msg Dateiname use a Schema/Aufgeloest/Feld workflow:
	- On focus: show schema text for editing.
	- On focus loss: resolve placeholders and show the resolved result.
	- When suggestions set schema values during cascade, Feld values are updated immediately to the resolved result so users can see suggestions without focusing the field.
- Input validation checks required values, invalid path/file characters, and path length limits.
- Optional attachment filing saves all attachments; long attachment names can be adjusted via rename dialog.
- On OK, the add-in creates the target folder, saves the mail as .msg, optionally saves attachments, and stores the session in SQLite.
- **The three notifications of a completed filing live in their own top-level window (`UI/NotificationToast.xaml`), not inside the task pane.** Previously they were Borders inside MailDropWpfTaskPane, which forced a choice: either the pane stayed open for as long as the message should be readable (~4.4 s of a 500 px sidebar standing around after the work was done), or the message disappeared with the pane. As a separate `Window` the toast outlives the pane, so the pane can be hidden *immediately* on OK while the message still gets its full duration. `NotificationToast` covers `ToastKind.Success`, `OverwriteWarning` and `DuplicateWarning`; it reuses the exact colour sets of the former inline Borders and carries the "Öffnen" link-style button for Success and Overwrite (Duplicate has none, unchanged from before). Durations are unchanged (Success 3.75s, Overwrite 6s, Duplicate 5s) - now that the toast costs no screen space, they could be raised independently of the pane if desired.
- The toast is positioned from `MailDropWpfTaskPane.GetScreenTopLeftDip()`, which must run **while the pane is still visible** (hence: position and target folder are captured first, the pane is hidden last). `PointToScreen` returns device pixels while `Window.Left/Top` expect DIPs, so the point is converted back via `PresentationSource.CompositionTarget.TransformFromDevice` - without that the toast lands in the wrong place on scaled (125 %/150 %) displays. `NotificationToast.xaml`'s `Grid` has a uniform `Margin="14"` on all four sides (room for the `DropShadowEffect`, which would otherwise be clipped at the window edge since the window is sized exactly to its content via `SizeToContent`), so `ShadowMargin` (the same 14, kept in code as a named constant) is subtracted from **both** `screenTopLeft.X` and `screenTopLeft.Y` - the visible border's left *and* top edges then line up exactly with the sidebar's left and top edges, symmetrically. An earlier version only subtracted it vertically and left the toast horizontally flush with `screenTopLeft.X` itself (window edge, not visible border) - deliberately meant to reproduce the removed inline notification's old `Margin="14,…"` by leaving the *visible* border indented 14px from the sidebar's left edge, but paired with the flush top edge this read as visibly misaligned/"verschoben" between the two axes; changed to flush-on-both-axes since that removed inline margin is no longer a real reference point to reproduce. The window is owned by Outlook's main window (`WindowInteropHelper.Owner` = `Process.GetCurrentProcess().MainWindowHandle`), which gets correct Z-order and minimize-with-Outlook behaviour for free instead of reimplementing it; if that fails it is logged and the toast is shown anyway, just uncoupled. `ShowActivated=False` keeps it from stealing focus. Deliberate simplification: the position is computed once at show time and **not** tracked afterwards, so moving the Outlook window during the ~4 s lifetime leaves the toast behind - accepted to avoid window-tracking complexity.
- "Öffnen" opens the just-filed Ablageordner (Session.LastSuccessfulAblageordner, set from checkedInput.CheckedAblageOrdner in ProcessSession right before Reset() clears the cascade state, and preserved across Reset() the same way LastDuplicateWarning/LastOverwriteWarning are) via Process.Start, and then closes the toast. The path is passed into the toast at construction rather than read back out of Session, so the toast has no dependency on Session state that Reset() may already have cleared. The user explicitly accepted that the button is now further from the mouse than when it sat directly under the OK button.
- `ShowSuccessNotification`/`ShowOverwriteWarningNotification`/`ShowDuplicateWarningNotification` are thin wrappers over `ShowFilingToast(kind, message, visibleDuration)`, which captures the anchor point and Ablageordner, closes any still-open previous toast (`_activeToast`), shows the new one and then calls `HideTaskPaneAfterFiling()`. The shared `ShowNotification(notification, visibleDuration, hideTaskPaneAfter)` helper that previously drove all four inline Borders was folded back into `ShowErrorNotification`: with the other three moved out to the toast window, it had exactly one caller left and its `hideTaskPaneAfter` parameter was always False, so the abstraction no longer earned its keep.
- `ErrorNotification` is the only remaining inline notification Border (Grid.Row="12") and still defaults to `IsHitTestVisible="False"`, toggled to True for its visible window by `ShowErrorNotification`. Background: `Opacity="0"` does not disable hit-testing in WPF, so an invisible Border still swallows clicks on whatever sits underneath it. While four Borders shared that one cell, the later-declared ones silently ate the clicks on the earlier ones' "Öffnen" button. With only one Border left the stacking conflict is gone, but the `IsHitTestVisible` toggle is kept because the Border still overlaps nothing-in-particular in that row and the same trap would return the moment a second inline notification is added. Same root cause as the OK/Abbrechen/i click-swallowing bug documented below.
- The task pane hides **immediately** after a successful filing (`ShowFilingToast` → `HideTaskPaneAfterFiling()`, which wraps `Globals.ThisAddIn.HideTaskPane()` in a Try/Catch logging via `Logger.LogError`). It no longer waits for the notification's fade-out, because the notification is no longer inside it. The error case is deliberately excluded and keeps its inline notification with the pane open: `ButtonOk_Click`'s branching shows that Success, Duplicate warning and Overwrite warning are the three outcomes of a `Session.ProcessSession()` call that already completed the filing (folder created, .msg saved, attachments saved, SessionRecord persisted) - `LastDuplicateWarning` comes from `InputChecker.CheckInput`'s informational "Bereits vorhanden: ..." check and never short-circuits `ProcessSession()`, unlike `checkedInput.ErrorMessage`, which returns early and is the only path reaching `ShowErrorNotification`. On an error nothing was filed and the user has to correct the input, so the message belongs next to the fields being corrected and the pane must stay.
- The task pane is also hidden automatically when the user switches Outlook modules away from Mail (Kalender, Kontakte, Aufgaben, Notizen, ...), via a new `_currentExplorer_FolderSwitch` handler (`Handles _currentExplorer.FolderSwitch`) in ThisAddIn.vb calling `HideTaskPaneIfNotMailFolder()`: this casts `_currentExplorer.CurrentFolder` to `Outlook.Folder` and hides the pane (only if it is currently visible) when `DefaultItemType <> Outlook.OlItemType.olMailItem`, then releases that Folder COM object via `Marshal.FinalReleaseComObject` in a Finally block - safe here (unlike the Explorer object itself, see the COM-release caveat below) since `CurrentFolder` returns a distinct RCW each call, not the same instance backing `_currentExplorer`. `Explorer.FolderSwitch` fires on every folder change in the explorer, including a module switch (each module shows its own default folder), so this covers any non-mail module generically rather than special-casing exactly Kalender/Kontakte; switching between two mail folders (DefaultItemType still olMailItem) does not hide the pane.
- A shared SuggestionEngine with ONNX embeddings is used for project path suggestion.
- The shared SuggestionEngine is lazy-loaded and preloaded in the background shortly after Outlook startup to reduce first task pane open latency.
- During session preparation, the engine precomputes feature distance lists between current mail/session and historical records, then scores a suggested ProjektPfad.
- Suggestion-relevant features are split into two groups: fixed features (Betreff, Datum, AbsenderDomain, Absender, AusfueBenutzer) are computed once per mail selection via dedicated per-feature subs called from PrepareSession(); mutable features (Titel, AblageordnerAufgeloest, ProjektPfad, ProjektstrukturPfad) are recomputed via dedicated per-feature subs triggered from the corresponding Session property setters and are zero-initialized at engine construction.
- Distance list allocation and initial computation are owned by CalculateInitialFeatureDistances(session) on SuggestionEngine, called once from PrepareSession() immediately after New(). New() handles only engine infrastructure (historical records); EmbeddingService is created lazily on first embedding generation.
- SuggestionEngine exposes SuggestProjektPfad, SuggestProjektstrukturPfad, SuggestTitel, and SuggestAblageordnerSchema, all backed by shared helpers. SuggestAblageordnerSchema and SuggestMsgDateinameSchema fall back to the DefaultSchemaTemplate (`[Datum (formatiert)]_[Absender (kurz)]_[Titel]`) when no suggestion passes the threshold, so schema fields always get a sensible default even on first use.
- An empty historical value is a legitimate, suggestible value for ProjektstrukturPfad, Titel, and AbsenderKurz - not every mail gets a Titel/AbsenderKurz, and an empty ProjektstrukturPfad means the TreeView's synthetic root node/ProjektPfad itself. SuggestProjektstrukturPfad/SuggestTitel/SuggestAbsenderKurz therefore use `Nothing` (not `String.Empty`) as their "no suggestion found" return value, so a real empty match isn't confused with "nothing found"; each also calls its shared search helper with `requireNonEmptyField:=False` so such records aren't filtered out of candidacy in the first place (`FindRecordsSortedByScore`/`FindBestRecordByField` default `requireNonEmptyField:=True`, which otherwise silently drops any historical record whose target-field value is blank). `RunSuggestionCascade` checks `suggested IsNot Nothing` for these three steps, not `IsNullOrWhiteSpace`. SuggestAblageordnerSchema also passes `requireNonEmptyField:=False` and can suggest an empty schema (a documented, legitimate value - see "leerer Ablageordner-Schema" in `IsInsideBaseFolder`'s note below), but didn't need the Nothing-sentinel change: its "no suggestion" fallback is already `DefaultSchemaTemplate` (never blank), which never collides with a real empty match, so `best?.AblageordnerSchema` already passed an empty match through correctly once candidacy allowed it. `SuggestProjektPfad` and `SuggestMsgDateinameSchema` were deliberately left on `requireNonEmptyField:=True`/the old empty-means-"no suggestion" behavior: ProjektPfad must be a real existing folder (empty is never a valid value, not just an underused one), and an empty MsgDateinameSchema would break the "gültiger Dateiname" requirement outright.
- The separate Pearson-correlation feature-weight learning in `RecalculateWeightsFromHistory` was updated to match: `GetThresholdInfo` (K/M distinct-value counting) and `GetTargetValues` (per-record target label array consumed by `TargetValuesMatch` in `ComputeWeightsForTarget`'s O(n²) pair loop) used to treat a blank target-field value as "unknown" - excluded from the K/M count, and mapped to `Nothing`, which `TargetValuesMatch` always treated as non-matching even against another blank. That meant two historical records that both legitimately left the same field empty were never counted as "the same target value" when learning which input features predict that field, so the weight-learning side had the identical blind spot as the old suggestion-generation sentinel bug, just one layer deeper. Both now normalize a blank value to `String.Empty` (a real, matchable category) instead of skipping/`Nothing`; `TargetValuesMatch` is now a plain `String.Equals` with no `Nothing`-guard, since `GetTargetValues` never produces `Nothing` anymore. This applies uniformly to every target field's threshold/weight computation (not just ProjektstrukturPfad/Titel/AbsenderKurz), since `GetThresholdInfo`/`GetTargetValues` are shared, generic, reflection-based helpers with no per-field special-casing (aside from the separately-handled boolean `AnhaengeAblegen`).
- SuggestProjektPfad and SuggestProjektstrukturPfad iterate candidates in score order (via FindRecordsSortedByScore) and return the first whose path actually exists on disk, skipping non-existent paths while still respecting the SuggestionScoreThreshold (`IO.Path.Combine(ProjektPfad, "")` resolves to ProjektPfad itself for the root-node case, which is already validated to exist). This avoids stale historical paths breaking the cascade.
- Internally, SuggestionEngine keeps FindBestRecordByField (returns single best record) for all fields except ProjektPfad/ProjektstrukturPfad, and FindRecordsSortedByScore (returns all above-threshold records sorted descending) for the two path fields. Avoids Func-signature overloading to prevent ambiguous lambda resolution in VB.
- For tracing/logging, SuggestionEngine passes explicit suggestion labels (e.g., ProjektPfad, MsgDateinameSchema) into the shared FindBestRecord helper instead of relying on lambda Method.Name.
- Session exposes SuggestXxx(value) methods that set the field value and then set the corresponding IsSuggestedXxx boolean flag to True. Cascade is driven by property setters: ProjektPfad → ProjektstrukturPfad → Titel → AbsenderKurz → AblageordnerSchema → MsgDateinameSchema → AnhaengeAblegen. Session also exposes IsSuggestedProjektPfad, IsSuggestedProjektstrukturPfad, IsSuggestedTitel, IsSuggestedAbsenderKurz, IsSuggestedAblageordnerSchema, IsSuggestedMsgDateinameSchema, IsSuggestedAnhaengeAblegen as full properties with PropertyChanged notification.
- MailDropWpfTaskPane.Session_PropertyChanged reacts to IsSuggestedXxx becoming True by showing the ✦ sparkle next to the field and (for ProjektstrukturPfad) dispatching a programmatic TreeView node selection via Dispatcher.BeginInvoke. The sparkle fades out when the user focuses/interacts with the field, which also sets the corresponding IsSuggestedXxx flag back to False (including AbsenderKurz, msg Dateiname and Anhänge ablegen).
- Default value for AnhaengeAblegen is True (checkbox always pre-checked). If the selected mail has no attachments, the checkbox is forced to False and grayed out (non-editable). Session.HasAnhaenge (read-only, computed from Anhaenge.Count > 0) drives this; SetEditMode special-cases CheckBoxAnhaenge to isEditable AndAlso Session.HasAnhaenge. The cascade's AnhaengeAblegen step is also skipped when HasAnhaenge is False.
- The attachment list (AttachmentScrollViewer) is controlled from code-behind: SetEditMode sets it to isEditable AndAlso Session.AnhaengeAblegen; Session_PropertyChanged(AnhaengeAblegen) updates it live so the list greys out immediately when the user unchecks the checkbox (even when attachments exist). The IsEnabled binding was removed from XAML to prevent SetEditMode from overriding it.
- ProjektPfad list shows the last 10 unique project paths (from DB) plus "anderes..." at the bottom, with a scrollable ListBox (MaxHeight="220"). DatabaseUtils.GetLastProjektVerzeichnisseForUser now exits the reader loop at count 10 (was 4). Its query uses `GROUP BY ProjektPfad ORDER BY MAX(AusfueDatum) DESC`, **not** `SELECT DISTINCT ... ORDER BY AusfueDatum DESC`: with DISTINCT, SQLite collapses the duplicate rows first and then sorts the remaining groups by an arbitrary (in practice the oldest) AusfueDatum of each group, so the list was not actually ordered by "most recently used" - a project used once long ago and again just now sorted to the back. Confirmed against SQLite directly (rows P1@2024, P2@2025, P1@2026 returned P2, P1 instead of P1, P2); `MAX(AusfueDatum)` per group fixes it. Note this depends on AusfueDatum being stored in a lexicographically sortable format, which System.Data.SQLite's default ISO-8601 DateTime serialization provides.
- A private _applyingTreeViewSuggestion flag guards TreeView1_SelectedItemChanged against treating the engine's programmatic node selection as a user interaction (which would reset IsSuggestedProjektstrukturPfad and hide the sparkle immediately).
- The info popup (help button `i`) is organized into four headed sections: "Ablageordner und msg Dateiname" (schema/placeholder usage, including the quoting syntax for fixed text (`"..."`) and how an unquoted separator between two placeholders is dropped when a neighboring placeholder is empty - see Placeholder reference below), "Vorschläge" (suggestions are generated for all fields and marked with ✦, based on prior mail filings), "Vorschlagsdaten exportieren" (SuggestionRecord transfer, copy `%APPDATA%/MailDrop/sessions.db`), and "Vorschläge verbessern" (contains the "Gewichte neu berechnen" button with explanation; the button is disabled while recalculation runs and re-enabled on completion via Dispatcher.Invoke).
- InfoPopup.xaml's visual style (indigo `#4F46E5` section-header accents, `#374151`/`#6B7280` body/muted grays, `#D1D5DB`/`#E5E7EB` borders, 4px CornerRadius, flat `SecondaryButton` style) is duplicated from MailDropWpfTaskPane.xaml's `UserControl.Resources` rather than shared, since the popup is a separate top-level `Window` and the project has no `App.xaml`/merged resource dictionary to share styles from. Placeholder variables render as rounded "chip" Borders in a WrapPanel instead of a plain vertical list. If the task pane's palette or button styles change, InfoPopup.xaml's copies need updating to match by hand.
- TextBoxAblageordner and TextBoxMsgDateiname each carry a short static WPF ToolTip (hover) summarizing the schema syntax in generic terms (`[Variable]` wird durch den Wert ersetzt; `"Text"` in Anfuehrungszeichen bleibt immer erhalten; ein Trennzeichen ohne Anfuehrungszeichen zwischen zwei `[Variable]` entfaellt, wenn eines leer ist) plus a pointer to the info popup for the full explanation and examples. Deliberately kept to 3-4 lines rather than duplicating the full info-popup text, since a hover tooltip disappears on focus/interaction and isn't meant for reading at length.
- Task pane button order (left to right): OK → Abbrechen → i.

## Runtime data and paths

- Session history database: %APPDATA%/MailDrop/sessions.db
- Error log (Release-safe): %APPDATA%/MailDrop/error.log, written by Helpers/Logger.vb's LogError(context, ex) for exceptions and LogInfo(context, message) for non-exception diagnostics (startup timing, version/environment info, dependency-file presence — see "Startup timing instrumentation" below). Release builds compile out Debug.WriteLine entirely (DefineDebug=false in MailDrop.vbproj), so this file is currently the only diagnostic trail available on an end-user machine; check it first when "the MailDrop button does nothing" or "the add-in got disabled" is reported. Both LogError and LogInfo never throw themselves (wrapped in Try/Catch) so logging failures cannot mask the original error or crash the caller. ThisAddIn_Startup unconditionally writes version/environment and dependency-check lines before doing anything else, so this file should now get at least those entries on every run that reaches Startup at all, even one that then fails — an entirely empty/missing error.log points to a failure before Startup was even invoked (CLR/ClickOnce/assembly load), not inside this project's own code.
- SQLite schema versioning uses `PRAGMA user_version`; `SessionDatabaseManager.CurrentSchemaVersion` defines the expected schema and `ApplyMigrations(...)` upgrades older databases.
- Database manager initialization is lazy: ThisAddIn.CurrentDatabaseManager creates SessionDatabaseManager on first access (not in ThisAddIn_Startup).
- ONNX model files are loaded from output folder path Models/model.onnx and Models/vocab.txt. These are the only committed copies of the model artifacts.
- **Repo cleanup (2026-09-20): removed unnecessary committed files from `development`.** Root-level `model.onnx`/`vocab.txt` were byte-identical duplicates of `Models/model.onnx`/`Models/vocab.txt` (~90 MB + ~230 KB), referenced by nothing (`MailDrop.vbproj`, `MailDrop.sln`, all code and docs only ever pointed at `Models/`) - almost certainly stale leftovers from before the `Models/` reorg. Deleted, and this file's earlier claim that they were deliberate "source artifacts" is corrected: they weren't. Also removed: `TestDirectory/` (already dropped in a prior commit, but this file's workspace-layout listing hadn't been updated to match) and the tracked `.claude/settings.json`, which held stale, single-use permission rules from a past session (a hardcoded commit-message-specific `Bash` allow rule, a Windows-local `Read(//c/Program Files/**)` path) rather than deliberate team-wide policy - not something that belongs in shared project config. If team-wide Claude Code settings are wanted here in the future, `.claude/settings.json` should be reintroduced deliberately with reviewed content, not left as incidental session output.

## Distribution (ClickOnce / GitHub Releases zip + network drive)

- Distribution channel: the ClickOnce `Publish` output (`setup.exe`, `MailDrop.vsto`, `Application Files/`, `Install-Certificate.ps1`) is zipped and attached to a GitHub Release; the same extracted zip is also copied onto a network drive. Anyone who wants to install runs `setup.exe` from either location. The `Publish/` folder itself is **no longer committed to git** (build output, `.gitignore`d) except `Publish/Install-Certificate.ps1`, which is hand-written source and stays tracked.
- Auto-update: `UpdateEnabled=true` and `UpdateMode=Background` in `MailDrop.vbproj`, with no hard-coded `UpdateUrl`/`InstallUrl`. ClickOnce then defaults to using the location an install ran *from* as its update source. Installing directly from the network drive means that path becomes the client's update source (checked in the background on every Outlook start, applied on next restart). Installing from a locally extracted GitHub Releases zip gets no auto-update; updating means reinstalling from a newer zip. `IsWebBootstrapper=False` since the network-drive/offline install still shouldn't assume internet access for .NET/VSTO prerequisites.
- **Known failure mode: `Temp\Deployment` access-denied during install/update.** Observed symptoms: (A) "update not possible" errors when a newer version is published even though a fresh install from the same location works; (B) right after a fresh install, Outlook auto-disables the add-in with a timeout-flavored message (see `DisabledItems` below), together with `System.Deployment.Application.DeploymentDownloadException` wrapping `System.UnauthorizedAccessException: Der Zugriff auf den Pfad "...\AppData\Local\Temp\Deployment\<random>\<random>\MailDrop.dll" wurde verweigert`. Both are the same underlying ClickOnce download step failing: on first run, `ClickOnceAddInDeploymentManager.InstallAddIn` copies files from the install location into the local VSTO add-in cache; on every later Outlook start, the background update check (see auto-update above) re-runs effectively the same download against that install location. **Note this is distinct from the separate, confirmed `ThisAddIn_Startup`-timing cause of an auto-disable documented under Current caveats below** (Outlook's own disabled-item message names a `Schwellenwertzeit`/`Benötigte Zeit` pair and "verursachte den langsamen Start" for that one, vs. this bullet's `DeploymentDownloadException` — check which one actually appears before assuming either cause.
  - Confirmed cause (from the stack trace itself): `System.Deployment.Application`'s download manager stages every downloaded file under a random subfolder of the purely local `%LOCALAPPDATA%\Temp\Deployment\` before reopening it to verify the manifest/signature; a sharing violation on that just-written staging file is a well-known, generic ClickOnce failure, most commonly caused by antivirus/EDR real-time scanning briefly locking newly written `.dll`/`.exe` files immediately after they're written (the deployment stack does not retry on this). This can happen regardless of where the install source lives, since the failing path is local, not the (possibly OneDrive-synced) source location.
  - One instance of this was observed with an install source inside a OneDrive-synced folder (`...\OneDrive - <Org>\...\MailDrop\`), which is not one of the two tested/supported install locations (plain network drive, or a zip extracted elsewhere — see above). Whether OneDrive as the source actually contributes to triggering the AV-lock race (e.g. via heightened scanning of files traced back to a cloud-sync origin) is **not confirmed** — the failing file itself is local and outside any OneDrive-synced tree, so this is a plausible risk factor and a reason to stick to the two supported locations, not a proven root cause.
  - This happens inside Outlook's own VSTO loader, before `ThisAddIn_Startup` runs, so none of this project's own Try/Catch guards (see below) can intercept or work around it — **it is not fixable via code in this repository.**

This certificate is not issued by a trusted CA, so installation on any machine other than the signing machine fails with a certificate/publisher-verification error.

This uses the `CurrentUser` store scope, which requires **no administrator rights** (chain building consults both `CurrentUser` and `LocalMachine` Root stores, so `CurrentUser\Root` alone is sufficient for that user's trust decisions). Supports `-Uninstall` to remove it again. End users run this once before running `setup.exe`; the script ships alongside `setup.exe` in the zip/network-drive folder.

Rationale: the compromised key is already neutralized at the trust layer (new certificate issued, `Install-Certificate.ps1` actively removes the old thumbprint from every user's `CurrentUser\Root`/`TrustedPublisher` stores on every run - see above), so the practical exploitability of the leaked key is already closed off without touching history. A force-push rewrite of every branch (`development`, all `claude/*` branches) would rewrite every commit hash repo-wide, break any existing local clones, and cannot fully succeed anyway since GitHub's own `refs/pull/N/head` refs for already-merged/closed PRs are server-managed and not push-writable - they would keep referencing pre-purge commits containing the blob regardless. Given that residual, unfixable exposure and the size of the collateral disruption, the leak is treated as remediated via rotation + active trust revocation, not via history rewrite. If this is revisited later, the prepared `git filter-repo` approach is known to work; it would still need a manual GitHub Support request to fully clear the blob from PR refs.
- The embedded certificate expires 2056-09-11. It only needs regenerating again if this new private key is ever compromised or replaced; in that case `Install-Certificate.ps1`'s embedded `$certBase64` block (plus adding its thumbprint to `$oldCompromisedThumbprints`), the local `MailDrop_1_TemporaryKey.pfx`, and the `ManifestCertificateThumbprint` in `MailDrop.vbproj` must all be regenerated/updated together, and every already-installed user must re-run the script for the new thumbprint (this is the one structural downside of self-signing vs. a CA-issued cert: cert rotation is not transparent to already-trusted clients - mitigated somewhat now by the script's active old-thumbprint removal, but installed users still don't get it automatically).

## Branching model

- **Single-branch model: `development` is the only ongoing branch.** The previous two-branch model (`development` for integration, a separate `released` branch as the PR-gated production/distribution source) was retired and `released` was deleted - it added a promotion step (`development` -> `released` via PR) without enough release cadence to justify a separate branch; `development`'s own head is now what gets published for distribution (see Distribution section) when a release is cut.

- Repository governance details (review gates and merge flow) are documented in CONTRIBUTING.md.
- GitHub default branch is `development` (this was already the actual default on the remote before `released` was deleted, despite `released` being documented as the intended default at the time - so deleting it required no default-branch change).

## Architecture and control flow

- Entry point: ThisAddIn_Startup in ThisAddIn.vb. Startup itself must stay fast and free of synchronous blocking work: Outlook measures its own call into this method and auto-disables the add-in if it takes too long (see `DisabledItems`/slow-add-in caveat below) — everything it does is either deferred to a background Task or a short UI-thread Timer tick, never executed inline.
- Ribbon action: MailDropRibbon -> Globals.ThisAddIn.MailAblegen_Click.
- Task pane creation: MailDropWpfHostControl hosts MailDropWpfTaskPane.
- Task pane default width is set during first creation in ThisAddIn.MailAblegen_Click (currently 500 px) and docked right.
- Selection updates: Explorer.SelectionChange -> MailSelected(), but only while the task pane is actually visible (`taskPane Is Nothing OrElse Not taskPane.Visible` short-circuits with an early Return before calling `MailSelected()`) - PrepareSession()'s work (mail metadata read, DB query, SuggestionEngine feature-distance/embedding computation) is otherwise invisible to the user and would just be wasted on every selection change while the pane is hidden or not yet opened. Safe because `MailAblegen_Click` always calls `MailSelected()` itself, before setting `taskPane.Visible = True`, so the pane is guaranteed to be freshly prepared for whatever is currently selected the moment it becomes visible again, regardless of how many selection changes were skipped while hidden.
- Module switches: Explorer.FolderSwitch -> HideTaskPaneIfNotMailFolder() (hides the task pane when the current folder's DefaultItemType is not olMailItem, i.e. any non-Mail Outlook module).
- Session preparation: Session.PrepareSession() -> Reset, mail metadata read, recent project paths load, shared SuggestionEngine access, feature distance precompute, suggested ProjektPfad apply (if valid).
- Save flow on OK: Session.ProcessSession() -> InputChecker -> create folder -> save .msg -> optional attachments -> persist SessionRecord -> geometric recalc-trigger check (see below; if due, RecalculateWeightsFromHistory in Task.Run on shared engine) -> reset session.
- SuggestionEngine pre-load: ThisAddIn_Startup fires PreloadSharedInstanceInBackground (SharedEngineLazy). Shared singleton loads historical records + computed weights from DB on first access.
- **Weight recalculation trigger is geometric, not a fixed interval.** `SuggestionEngine.ShouldRecalculateWeights(recordCount, Optional growthFactor As Double = 1.25) As Boolean` (`Friend Shared`, a pure function of `recordCount` alone) returns True iff `recordCount` is exactly one of the geometrically-spaced milestones 1, 2, 3, 4, 5, 7, 9, 12, 15, 19, 24, 30, 38, 48, 60, 75, 94, ... (`milestone_(i+1) = Math.Max(milestone_i + 1, Math.Ceiling(milestone_i * growthFactor))`, `milestone_0 = 0`) - i.e. recalculates roughly every time the dataset has grown ~25% since the previous milestone, not every fixed N sessions. Replaced the previous fixed `recordCount Mod 50 = 0` check. This milestone sequence depends only on `growthFactor`, not on whether/when a previous recalculation actually ran or was persisted, so membership is decided by simulating the sequence from `recordCount`'s own value - no DB lookup or persisted trigger state at all (an earlier version queried `SELECT MAX(RecordCount) FROM ComputedWeights` via a since-removed `SessionDatabaseManager.GetLastWeightRecalcRecordCount()` to reconstruct "record count as of the last recalculation"; unnecessary, since the deterministic sequence makes that reconstruction redundant, and a DB round-trip on every `ProcessSession()` is strictly more expensive than the O(log_growthFactor(recordCount)) in-memory loop, ~40 iterations even at 10,000 records). Rationale (full derivation in the function's own code comment): `RecalculateWeightsFromHistory` is O(n²) (pairwise loop × 7 target fields), while the statistical value of each additional data point shrinks as O(1/√n) (Pearson estimator precision) - a fixed interval means lifetime total recompute cost grows cubically in record count (Σ(50i)² ~ n³), whereas the geometric milestone sequence needs only O(log n) recomputations whose cost sum is dominated by (and stays within a small constant factor of, ~2.3× for growthFactor=1.25) the single most recent, largest recomputation. Early on this fires on nearly every save, when recomputation is cheap and each new record can still meaningfully shift the weights; the interval widens automatically as the history grows.
- Feature weights are data-driven per target field when sufficient history exists. Weights are computed via pairwise Pearson correlation between feature similarity vectors and a binary label (same/different target value for each record pair), clipped to [0, ∞) and normalized to sum 1. Stored per target field in the ComputedWeights SQLite table (columns: TargetField, FeatureName, Weight, RecordCount, ComputedAt). Loaded into _computedWeights As Dictionary(Of String, Dictionary(Of String, Double)) during SuggestionEngine.New(). Threshold per target field: ≥3 distinct values each appearing ≥2 times (AnhaengeAblegen: both True and False ≥2 times). Fallback to per-target hardcoded weights (GetFeatureWeightsForXxx) when threshold not met or no stored weights exist. Recalculation is triggered per the geometric schedule above and also via the "Gewichte neu berechnen" button in the task pane (unconditional, ignores the trigger).
- Cascade-aware feature sets: for each target field, only features causally available at that cascade stage are included in the correlation computation. Fixed input features (Betreff, Datum, AbsenderDomain, Absender, AusfueBenutzer, AusfueDatum) are always available. Mutable features become available in cascade order: ProjektPfad from ProjektstrukturPfad onwards, ProjektstrukturPfad from Titel onwards, Titel from AbsenderKurz onwards, Ablageordner from MsgDateinameSchema onwards. The mapping is encoded in MutableFeatureAvailableFromStep (Dictionary keyed by feature name, value = CascadeStep enum) — the cascade order itself is not redefined, only the input-availability dependency. PearsonCorrelation returns Double.NaN when the feature vector is constant (all pairs have identical similarity), handled in debug output as "Feature-Vektor konstant". RecalculateWeightsFromHistory emits structured Debug.WriteLine output per target field: K/M threshold info, per-feature Pearson value with reason, skipped cascade features, and normalized before/after weight comparison.

## Placeholder reference

Supported placeholders for Ablageordner and msg Dateiname:

- [Titel]
- [Absender]
- [Absender-Domain]
- [Empfaenger]
- [Empfaenger (kurz)]
- [Betreff]
- [Datum]
- [Datum (formatiert)]
- [Absender (kurz)]

Note:
- [Empfaenger (kurz)] currently resolves to the same value as Empfaenger.
- Fixed/literal text in a schema can be forced by wrapping it in double quotes, e.g. [Titel]" (Entwurf) "[Absender (kurz)] - the quoted text is always emitted verbatim (quotes stripped), regardless of whether neighboring placeholders are empty. Any other (unquoted) text that sits directly between two placeholders - e.g. the "_" in the default schema - is treated as a connector/separator rather than fixed text, and is only emitted when it actually ends up joining two placeholders that both resolved to a non-empty value (see below). Unquoted text that does not sit between two placeholders (e.g. a fixed prefix before the first placeholder) is not a connector and is always emitted unchanged, quotes or not.
- Session.ReplacePlaceholders (Core/Session.vb) parses the schema template into SchemaSegment values of kind Literal (quoted text, or any text not sandwiched between two placeholders), Connector (unquoted text directly between two placeholders), or Placeholder (a resolved value, possibly empty), via a single regex matching both a quoted-string pattern and the known placeholder tokens; unmatched substrings between tokens ("gaps") are classified as Connector only when both their immediate neighbors are Placeholder segments, Literal otherwise. Resolution is then a "skip-empty-join": a Connector is held back (pendingConnector) instead of appended immediately, and only actually emitted right before the next non-empty Placeholder that follows a previously-emitted non-empty Placeholder; an empty Placeholder is skipped without discarding a still-pending connector (a later Connector simply overwrites it). This guarantees exactly one connector between any two placeholders that actually resolved to a value, however many empty placeholders sit between them, and never leaves a leading or trailing connector - independent of quoting. Example: "[A]_[B]_[C]" with only B empty resolves to "A_C" (not "AC" or "A__C"); with both B and C empty it resolves to "A" (no trailing "_"); [A]" - "[B] with B empty still resolves to "A - " because the quoted " - " is fixed text, not a connector.

## Current caveats and implementation notes

- **Outlook's slow-add-in auto-disable ("Dieses Add-In hat den langsamen Start von Outlook verursacht", `Schwellenwertzeit` 1000 ms) is still unresolved — an earlier fix here was necessary but confirmed NOT sufficient.** `ThisAddIn_Startup` no longer touches `Application.Explorers`/`ActiveExplorer()`/`Session` synchronously: that call used to be the first line of `Startup` and can block on Outlook's own mail-store/session init (Exchange cached-mode sync, PST/OST mounting), a real, known VSTO pitfall, so it's deferred to a short (100 ms) `System.Windows.Forms.Timer` tick, the same UI-thread-deferral pattern `PreloadTaskPaneInBackground` already used for task pane creation (a `Timer` tick is COM-safe for STA-affine `Explorer` objects; `Task.Run` is not, since it would hand the COM call to a non-UI thread). `MailAblegen_Click`'s ribbon-click path is unaffected since it doesn't depend on `_currentExplorer`; only automatic `SelectionChange` reactivity is delayed by the same ~100 ms at startup. **However**, after this fix shipped (v1.0.4.0) and was confirmed installed, the exact same disable recurred with `Benötigte Zeit` of 1765 ms — statistically indistinguishable from the pre-fix occurrences (1765-2032 ms) — meaning `Application.Explorers` was at most a partial contributor, not the dominant cost. The likely explanation: Outlook's watchdog measures the *entire* VSTO add-in load (CLR bootstrap, ClickOnce manifest/version verification, loading and JIT-compiling `MailDrop.dll` and its sizeable dependency closure — ONNX Runtime, Protobuf, several `Microsoft.Bcl.*` polyfills, SQLite), not just `ThisAddIn_Startup`'s own Sub body, so no amount of rearranging code inside that Sub can fix a bottleneck that occurs before the Sub is even called. This is unconfirmed, not yet proven, since it can't be profiled from outside a real Outlook process.
  - **Startup timing instrumentation** (added to get real field data instead of guessing again): `ThisAddIn_Startup` and the deferred explorer-wiring timer tick each write their own elapsed time via the new `Logger.LogInfo(context, message)` (Helpers/Logger.vb, same `%APPDATA%\MailDrop\error.log` file as `LogError`, but for non-exception info — this survives `DefineDebug=false` Release builds the same way `LogError` does, unlike every existing `Debug.WriteLine` trace in this startup path, which is compiled out of Release entirely and was therefore useless for diagnosing this on an end-user machine). On the next occurrence, check `error.log` for `[Startup timing]` entries: if `ThisAddIn_Startup Sub body returned after` reports a small number (a few ms, as expected post-fix) while Outlook still reports a `Benötigte Zeit` in the seconds, that confirms the bottleneck is before `Startup` runs at all (CLR/ClickOnce/JIT, likely compounded by antivirus/EDR scanning each loaded DLL — the same AV theme recurring across the `Temp\Deployment` failure and the `.NET Runtime` profiler-attach noise seen while investigating this), and further fixes need to target the load/dependency footprint rather than this Sub's body. If it instead reports a similarly large number, the deferral has a bug or something else in the Sub is still blocking.
  - **Gap found while investigating a further recurrence on 2026-09-16: `error.log` did not exist at all on the affected machine.** Root cause: `ThisAddIn_Startup`'s body was not wrapped in `Try/Catch`, and the *only* `Logger.LogInfo` call was the very last line — so any exception thrown anywhere in the Sub (explorer-timer construction, `SuggestionEngine.PreloadSharedInstanceInBackground`, `PreloadTaskPaneInBackground`, a static-initializer failure, etc.) propagated out of `Startup` unhandled and left zero trace, including not creating `%APPDATA%\MailDrop` at all if it was the very first run. Whether VSTO/Outlook's resiliency tracking treats a thrown `Startup` exception the same as a slow load (i.e. whether this was *also* contributing to the auto-disable itself, not just hiding evidence of it) is unconfirmed but plausible. Fixed/added in `ThisAddIn.vb`:
    - `ThisAddIn_Startup`'s body (after handler registration and the always-run logging calls below) is now wrapped in one `Try/Catch` that logs any exception via `Logger.LogError("ThisAddIn_Startup", ex)` instead of letting it propagate — `Startup` itself should now never throw out to Outlook.
    - `AppDomain.CurrentDomain.UnhandledException` and `TaskScheduler.UnobservedTaskException` handlers are registered as the first two lines of `Startup` (`OnUnhandledException`/`OnUnobservedTaskException`), logging via `Logger.LogError`/`Logger.LogInfo`, to catch exceptions on background threads that the Sub-level `Try/Catch` cannot see (e.g. a faulted `Task` from the engine preload that's never awaited/observed).
    - `LogStartupEnvironmentInfo()` and `LogDependencyFilePresence()` log under contexts `"Startup version info"`/`"Startup dependency check"`: assembly version + file version, the DLL's `LastWriteTime` as a build-date approximation (no embedded linker timestamp is read), whether the process is ClickOnce-deployed (`System.Deployment.Application.ApplicationDeployment.IsNetworkDeployed`) plus its `CurrentVersion`/`UpdateLocation` when it is (distinguishes a real ClickOnce install from a local `vstolocal` VS debug registration — the two are easy to conflate when troubleshooting a "disabled after install" report), Outlook's `Application.Version`, OS version, 32/64-bit process, CLR version, process start time, elapsed time between process start and `Startup` being entered (a proxy for CLR/ClickOnce/JIT overhead *before* `Startup` was called), and whether `x86\SQLite.Interop.dll`, `x64\SQLite.Interop.dll`, `Models\model.onnx`, `Models\vocab.txt` exist relative to `AppDomain.CurrentDomain.BaseDirectory` (surfaces the known `SQLite.Interop.dll` flattening/deployment problem — see Distribution section — at startup instead of waiting for a later `DllNotFoundException`). Requires the new `<Reference Include="System.Deployment" />` in `MailDrop.vbproj`. **Originally called synchronously as the first thing in `Startup`; moved to a short (10 ms) deferred `System.Windows.Forms.Timer` tick after field data (2026-09-16, see below) showed this synchronous logging itself cost ~420 ms of Startup's own measured body time** (`System.Deployment.Application` assembly load + reflection + four `File.Exists` calls are not free on a cold/first run) — ironic given the whole point was diagnosing slowness. Only the plain `Logger.LogInfo("Startup", "ThisAddIn_Startup entered.")` proof-of-life line stays synchronous now.
    - `ThisAddIn_Shutdown` now also logs (`"Shutdown"` / `"ThisAddIn_Shutdown entered."`) so the log timeline can distinguish a clean Outlook exit from a crash/kill (no Shutdown line before the next Startup) or an auto-disable (no Startup line at all for a run).
    - Net effect: even a total, unanticipated Startup failure now leaves at least the version/environment/dependency lines (unless the failure happens within the first ~10 ms, before the deferred timer fires) and, if the exception was in the Sub's own body, the `Logger.LogError` entry in `error.log` — "there is no error.log at all" should no longer happen for any failure that gets as far as this DLL being loaded and `Startup` being invoked. It cannot help with a failure that occurs *before* `Startup` is invoked (CLR bootstrap, ClickOnce manifest verification, assembly load itself) — that class of failure remains invisible to this project's own code, per the point above.
  - **First real field data, 2026-09-16 18:48 (fresh install, same-session disable/close observed)**: `error.log` showed `ProcessStartTime=18:48:10` → `Startup entered` at `18:48:14` (**3847 ms already elapsed before `Startup` ran at all**), then `ThisAddIn_Startup Sub body returned after 420 ms` (before the deferral fix above existed) — total ≈4.2 s against the ~1000 ms watchdog threshold, consistent with the slow-start disable and confirming the pre-`Startup` CLR/ClickOnce/JIT cost as the dominant factor (code inside `Startup` cannot fix ~3.8 s that elapses before it's even called). `ThisAddIn_Shutdown` then logged only ~2 s after `Startup` returned; whether that was the disable mechanism tearing the add-in down mid-session or just the user closing Outlook is not distinguishable from the log alone — would need the exact Outlook disable-dialog wording or a fresh `DisabledItems`/`CrashingAddinList` registry read from that machine to confirm.
  - **OneDrive as install source ruled OUT as the dominant cause (three field tests, 2026-09-16).** Two runs from `OneDrive - SIERA\10_Software\MailDrop\MailDrop.vsto` and one from `C:\Users\<user>\Documents\MailDrop\MailDrop.vsto` (confirmed a plain local folder, not OneDrive/Known-Folder-Move-redirected) gave essentially the same numbers:

    | Run | Source | Pre-`Startup` (ms) | `Startup` body (ms) | Total (ms) |
    |---|---|---|---|---|
    | 1 | OneDrive | 3847 | 420 | 4267 |
    | 2 | OneDrive | 3633 | 409 | 4042 |
    | 3 | Documents (local) | 3307 | 384 | 3691 |

    Moving off OneDrive did not meaningfully change either number — the mild downward trend is at least as plausibly explained by antivirus/EDR increasingly caching a "known good" verdict for the mostly-unchanged dependency DLLs (ONNX Runtime, Protobuf, SQLite — only `MailDrop.dll` itself actually changes between publishes) as by install location. This downgrades the OneDrive risk factor documented in the Distribution section back to "not confirmed as a contributor" — it may still be worth avoiding on general principle (untested combination, `Temp\Deployment` AV-lock risk), but it is not the explanation for the slow load itself. Also notable across all three runs: `Startup`'s own body time (384-420 ms) barely moved even after `LogStartupEnvironmentInfo`/`LogDependencyFilePresence` were deferred off the synchronous path (see above) — strong evidence that number is dominated by one-time JIT/shadow-copy cold-start cost inherent to any code executing for the first time after a fresh ClickOnce install (a new `AppData\Local\assembly\dl3\...` cache entry every publish), not by any specific line of code that can be further optimized away.
  - **New hypothesis with a concrete fix applied: `generatePublisherEvidence`.** The ~3.3-3.8 s elapsed *before* `Startup` is even called, consistent across all three runs regardless of install source, matches a well-documented .NET/ClickOnce symptom: the CLR's Authenticode "publisher evidence" check for a signed assembly performs a network CRL/OCSP revocation lookup before the assembly runs, and on a network where that lookup is slow or has to time out (corporate proxy/firewall, no direct route to a CRL endpoint), this reliably adds multiple seconds of startup latency — independent of where the install source files live, since the check is against the *certificate*, not the file location. MailDrop's manifests/assemblies are signed (self-signed cert, see Distribution section above), so this applies. Fix applied: `app.config` now sets `<generatePublisherEvidence enabled="false" />` inside `<runtime>`, disabling this check (deploys as `MailDrop.dll.config` next to the DLL, confirmed via a local build). **Unverified in the field yet** — needs a fresh publish + install + reproduction with the updated `error.log` to confirm the pre-`Startup` elapsed time actually drops.
  - **Outlook's resiliency tracking persists across reinstalls/republishes and is a separate mechanism from any file/ClickOnce cache.** `HKCU:\Software\Microsoft\Office\16.0\Outlook\Resiliency\CrashingAddinList` keeps a per-add-in (hashed identity) rolling counter of slow/crashing loads, distinct from `DisabledItems` (which only lists add-ins *currently* disabled) — an add-in can have a non-zero crash count here without being in `DisabledItems` yet. Observed non-empty on a MailDrop dev machine (three hashed entries) while `DisabledItems` was empty at the same time. Practical implication: publishing a fixed build does not reset this counter, so a machine with prior slow-load history may disable a genuinely-fixed build faster/more easily than a machine with no history — when troubleshooting, check both `DisabledItems` and `CrashingAddinList`. **Confirmed reset procedure for a clean test** (Outlook fully closed first): remove MailDrop's own `DisabledItems` entry (decode each value name's UTF-16 bytes, match on `MailDrop`, `Remove-ItemProperty` just that one), then `Remove-Item` the entire `CrashingAddinList` key (its entries are opaque hashed IDs with no readable add-in name, so there's no way to target only MailDrop — deleting the whole key resets the strike counter for every Outlook add-in on that profile, which is harmless), then `rundll32.exe dfshim.dll CleanOnlineAppCache` to also drop the separate ClickOnce deployment cache before reinstalling/retesting.
- SuggestionEngine uses weighted scoring across Betreff (semantic cosine similarity), Datum (normalized date similarity), AbsenderDomain (categorical match), Absender (categorical match), AusfueBenutzer (categorical match), Titel (text similarity), Ablageordner (text similarity), ProjektPfad (categorical match), and ProjektstrukturPfad (categorical match).
- Feature weights are defined per suggestion target in Core/SuggestionEngine.vb (separate weight profiles for ProjektPfad, ProjektstrukturPfad, Titel, AblageordnerSchema, MsgDateinameSchema, AnhaengeAblegen) and are applied independently during score aggregation.
- For Titel suggestions, Betreff dominates (0.55) so that semantic mail content drives the Titel choice. ProjektstrukturPfad weight is 0 to prevent a self-reinforcing cascade bias (ProjektstrukturPfad was itself suggested from the same historical record earlier in the cascade, so giving it weight here would circular-reinforce the same record). Ablageordner and Titel weights are 0 because both are mutable features initialized to zero and not yet set in the cascade when Titel is suggested.
- Distance lists are initialized with zeros at construction (length = historical record count). Fixed-feature subs overwrite them in PrepareSession(); mutable-feature subs overwrite them incrementally as the user edits fields.
- Current feature weighting is heuristic constants in Core/SuggestionEngine.vb and may need tuning with real usage data.
- Core/SuggestionEngine.vb relies on explicit framework imports (System, System.Collections.Generic, System.Linq) and uses a VB Char literal "\"c as one of the token separators in TokenizeForSimilarity.
- In Core/InputChecker.vb, ablageOrdnerPfad is Path.Combine(projektstrukturPfad, session.AblageordnerAufgeloest) where projektstrukturPfad is already the fully-combined absolute path. (A previous version incorrectly prepended projektPfad a second time, duplicating path segments — fixed.)
- Text encoding/comments show mixed umlaut encoding artifacts in several files; prefer preserving existing file encoding unless intentionally normalizing.
- SuggestionEngine.New() wraps GetAllSessionRecords() in try-catch and defaults to an empty list on failure so the Lazy never becomes permanently broken.
- EmbeddingService implements IDisposable; the InferenceSession is released via Dispose().
- SuggestionEngine implements IDisposable and exposes DisposeSharedInstance(); ThisAddIn_Shutdown calls it so ONNX resources are deterministically released when Outlook exits.
- GetEmbeddingService() returns Nothing if EmbeddingService construction fails (model files missing); all callers use null-conditional access so embedding gracefully degrades to zero similarity.
- MailUtils and InputChecker now release Outlook COM objects (MailItem, Attachment) via Marshal.FinalReleaseComObject in Finally blocks to reduce long-running COM reference buildup. The Explorer object is deliberately excluded from this in every MailUtils function (ReadMailMeta, ReadAttachmentNames, SaveSelectedMailAsMsg, SaveMailAttachments): `app.ActiveExplorer()` returns the same RCW instance as ThisAddIn's `WithEvents _currentExplorer` field. Calling FinalReleaseComObject on it (as SaveSelectedMailAsMsg/SaveMailAttachments briefly did) separates that RCW from its underlying COM object and permanently breaks the Explorer.SelectionChange event connection for the rest of the Outlook session — after that, MailSelected() only ever runs again when MailAblegen_Click calls it directly (i.e. the ribbon button/task-pane-open path), not on further mail selection changes, until Outlook is restarted. This was the root cause of a bug where MailDrop stopped reacting to mail selection changes shortly after a mail was filed (OK button), and only "recovered" for a single selection each time the task pane was reopened via the ribbon button.
  - Not to be confused with the separate, intentional early-Return in `_currentExplorer_SelectionChange` (see "Selection updates" above) that skips calling `MailSelected()` while `taskPane.Visible` is False: that one is a resource-saving no-op, not a broken connection — the event still fires and is still handled on every selection change, it just does nothing when nobody can see the result. Unlike the COM-release bug above, it self-corrects the instant the pane is shown again, since `MailAblegen_Click` calls `MailSelected()` unconditionally right before setting `Visible = True`.
- Dispatcher.BeginInvoke calls in MailDropWpfTaskPane guard against Dispatcher.HasShutdownStarted before posting.
- ThisAddIn.MailAblegen_Click, the Explorer.SelectionChange handler, and PreloadTaskPaneInBackground each wrap their work in Try/Catch and call Logger.LogError on failure, instead of letting exceptions propagate to the VSTO ribbon/event boundary. This matters because Outlook/VSTO silently swallows unhandled exceptions thrown from ribbon callbacks and COM event handlers (no dialog, no visible effect) unless the user has enabled Outlook's "Show add-in user interface errors" option — without the Try/Catch, a failure anywhere in MailSelected() -> Session.PrepareSession() (e.g. first-time SQLite/ThisAddIn.CurrentDatabaseManager init failing) meant the button click did nothing observable and left no trace. taskPane.Visible = True in MailAblegen_Click now always runs as long as the task pane itself was created, even if populating it (MailSelected) failed, so the pane is shown (possibly not fully populated) rather than the click appearing to do nothing; if task pane creation itself fails, a MessageBox is shown pointing at error.log since there is nothing else to display.
- MailDropWpfTaskPane.SetEditMode(isEditable) iterates all controls via FindVisualChildren(Of Control) and now wraps each control's IsEnabled assignment in its own Try/Catch (logs via Logger.LogError and continues) instead of one Try/Catch around the whole loop, so one control failing to update can't leave later controls stuck at their previous IsEnabled value. FindVisualChildren itself also wraps each VisualTreeHelper.GetChildrenCount/GetChild call individually (Yield is not allowed inside a VB Try block that has a Catch, so the recursive descent and the error handling had to be split into separate Try blocks with no Yield inside them): a subtree that fails to enumerate (e.g. ListBox1/TreeView1 item containers not yet generated) is logged and skipped instead of aborting the entire enumeration, which previously could leave arbitrary controls after the failure point permanently disabled/greyed out with no trace of why.
- **Open performance issue (not yet fixed): BuildDirectoryTree walks the whole project folder eagerly, up to 20 levels deep, on the UI thread.** `Session.ProjektPfad`'s setter calls `BuildDirectoryTree()`, which is reached on *every* mail selection (the cascade suggests a ProjektPfad → setter fires), and `CreateDirectoryNodeWithExpand` then recurses through `Directory.GetDirectories` for the entire subtree. Since BuildDirectoryTree passes `expandByDefault:=False`, the tree is rendered fully collapsed - so for a large project folder on a network drive nearly all of that enumeration is latency the user waits for without seeing any of it. This is very likely the dominant real-world delay when switching mails, more so than anything in the suggestion engine. The proper fix is lazy child loading (populate a node's children on TreeViewItem expansion, with a placeholder child to keep the expander arrow), but it is not a local change: `FindTreeViewItem` walks the node tree to apply a ProjektstrukturPfad suggestion and to re-select after folder actions, so it would need to force-load along the target path. Deliberately left alone here because it changes UI behaviour and cannot be validated without a real Outlook session.
- DirectoryTreeHelper.CreateDirectoryNodeWithExpand accepts an optional maxDepth parameter (default 20) to prevent StackOverflow from deep or cyclic directory structures. It also accepts an optional expandByDefault parameter (default True) controlling whether nodes at level<=2 start expanded: RefreshChildren (folder create/delete/rename) keeps expandByDefault:=True, matching the documented post-edit "show two levels" behavior above; BuildDirectoryTree passes expandByDefault:=False so a fresh tree (built whenever ProjektPfad is set, including as part of the suggestion cascade) starts fully collapsed instead of pre-expanding the first two levels regardless of any ProjektstrukturPfad suggestion.
- MailDropWpfTaskPane.FindTreeViewItem (used both to apply a ProjektstrukturPfad suggestion's programmatic TreeView selection and by SelectTreeViewPath after Neuer Ordner/Loeschen/Umbenennen) walks only the ancestor chain toward the target RelativePath and expands (IsExpanded = True) exactly those ancestor nodes, via IsAncestorRelativePath (a real-prefix check on RelativePath, separator-bounded). Previously it expanded every visited node before comparing paths, so searching for a suggested/target node also fully expanded whichever sibling branches were visited first during the depth-first walk - combined with BuildDirectoryTree's old level<=2 default this looked like "the whole tree expands" on every new-mail selection with a ProjektstrukturPfad suggestion. Now, combined with BuildDirectoryTree starting fully collapsed, only the suggested/selected node's own ancestor path is expanded. IsAncestorRelativePath special-cases an empty candidateRelativePath (the synthetic root node) as an ancestor of any non-empty target, since a plain prefix check would otherwise never descend past the root - without it, FindTreeViewItem/SelectTreeViewPath couldn't reach any real folder once the root node was introduced.
- **Pitfall: VB's string `<>`/`=` operators treat `Nothing` and `String.Empty` as equal**, which matters now that `Session.ProjektstrukturPfad` uses `Nothing` ("nothing selected") and `String.Empty` (synthetic root node selected) as two distinct, meaningful values. `ProjektstrukturPfad`'s setter therefore compares with `String.Equals(_projektstrukturPfad, value)` instead of `<>` - with `<>`, selecting the root node for the first time (a `Nothing` → `""` transition) would silently no-op (no `OnPropertyChanged`, no cascade, and after the next `Reset()` the field could get stuck on `""` instead of actually returning to `Nothing`, permanently breaking the "not yet selected" validation state). Similarly, `SelectTreeViewPath`/`FindTreeViewItem` distinguish `relativePath Is Nothing` (skip) from `relativePath = String.Empty` (select the root node) rather than using `String.IsNullOrWhiteSpace`.

Session.HasAnhaenge (Anhaenge.Count > 0) is raised via OnPropertyChanged after ReadAttachmentNames and after Anhaenge.Clear() in Reset.

Without it, the background `PreloadEmbeddingService` (Task.Run from ThisAddIn_Startup) and the UI thread (PrepareSession → RecalculateBetreffDistances → GetOrCreateCurrentBetreffEmbedding) could both observe the field as Nothing and each construct an EmbeddingService - loading the ONNX model twice and leaking the InferenceSession that loses the race, since the field only keeps one. Reachable whenever the user opens the task pane inside the ~1.5 s preload window.

Necessary because those paths are built with `Path.Combine` from freely editable fields (schema, Titel): `Path.Combine` silently **discards its first argument** as soon as the second is rooted (`C:\...`, `\...`), and `..` segments walk out of the project folder - either way the mail would have been filed outside the project with nothing indicating it. - Performance work in the suggestion path (all verified behaviour-preserving, none of it changes scores or suggestions):
  - `Session.ReplacePlaceholders` no longer builds and compiles a new `Regex` per call (it runs on every Titel/schema change and in every cascade step); the pattern depends only on the constant placeholder keys and is cached in the shared `_placeholderRegex` via `GetPlaceholderRegex`. Only the *values* dictionary is still rebuilt per call.
  - `FindRecordsSortedByScore`/`FindBestRecordByField` resolve the ten feature weights once per search (`FeatureWeight`) instead of doing ten dictionary lookups per record; `WeightedFeatureScore` was replaced by plain multiplication in the score expression.
  - `CalculateTextSimilarity` was split into `TokenizeToSet` + `JaccardSimilarity` (+ `CalculateTextSimilarityWithTokens` for a precomputed constant side). `RecalculateTitelDistances`/`RecalculateAblageordnerDistances` now tokenize the current value once per run instead of once per historical record, and `ComputeWeightsForTarget` precomputes one token set per record instead of re-tokenizing both sides of every O(n²) pair. The union size is derived as `|A| + |B| - |A∩B|` instead of materializing LINQ `Intersect`/`Union` sequences.
  - `ComputeGlobalMaxDateDistance` is O(n) (max date − min date, clamped to ≥ 1.0) instead of an O(n²) pair scan - mathematically the same value.

  - `GetAllSessionRecords` parses Datum/AusfueDatum via `ParseDateOrMin` (`DateTime.TryParse`, falling back to the existing `Date.MinValue` "missing" sentinel). A single NULL or unparseable date previously threw a FormatException out of the whole method, and since both callers only catch and continue with an empty list, that would have silently disabled the entire suggestion history.

## Conventions for Claude Code contributions

- Keep domain terms and UI labels in German to match existing code and user-facing text.
- Favor minimal, targeted edits; do not refactor broad areas unless needed for the requested change.
- Preserve the Session-based flow (PrepareSession/ProcessSession) and avoid introducing parallel state objects.
- For UI behavior changes, keep data-binding centered on Session properties and existing control names.
- For persistence changes, keep SessionRecord schema and SQLite migration impact explicit.
- When touching SuggestionEngine, keep behavior behind existing calls to avoid breaking current filing flow.
- Whenever code is changed, also review and update this CLAUDE.md so implementation notes, behavior descriptions, and caveats stay in sync.

## Response style and process transparency

- Answer critically, not just confirmatively. If a request is ambiguous, incomplete, or conflicts with existing architecture, say so explicitly before implementing.
- Every response that involves a task must state clearly whether: (a) a concept described in this CLAUDE.md or in the conversation was **translated into code** (no conceptual change), or (b) the concept itself was **updated** (the design changed during implementation). If (b), update the relevant section of CLAUDE.md to reflect the actual implemented design before closing the task.
- At the end of every response, include a short **"Next steps"** suggestion — one to three concrete items the project should address next, whether that means writing more code, refining a concept, or updating documentation. Base it on the current state of the codebase and known open issues.
